## Architecture

The repo is now a **three-machine workflow**:

```
Mac dev workstation                  Colab (Pro)                Raspberry Pi 5 + AI HAT+ 2
─────────────────────                ────────────               ───────────────────────────
authors all code                     trains weights             executes inference + benchmarks
                                                                hosts datasets
   │                                    │   ▲                       │   ▲
   │  git push (master)                 │   │ git clone + curl       │   │ git pull
   ▼                                    ▼   │   Zenodo               ▼   │
GitHub (public): AKarode/strawb-analysis ←──┴────────────────────────┘
                                            │
                            best.pt ────────┘ (via Drive mount + browser download)
```

Cursor on the Pi (accessed only via Raspberry Pi Connect — no SSH) executes Mac-authored code and reports back via paste. Mac authors, Pi executes; Colab is the GPU layer that bridges them.

## Key design decisions

| Decision | Why |
|---|---|
| Public repo over deploy keys | Simplest way to `git clone` onto the Pi without managing PATs/keys. Source code is MIT; no weights, datasets, or credentials in the repo. |
| AGENTS.md as cross-tool contract | Cursor on the Pi needs role boundaries (execute-only, no master pushes, no scanner edits) but the same file works for Codex / Aider / Claude Code on the Pi if we ever swap agents. |
| Lazy ultralytics import in `train_detect.py` | `--help` works on the Mac without the heavy ML deps installed. Forces the import to fail loudly only when actually running training. |
| Materialize data yaml at runtime instead of committing one | Ultralytics resolves `path:` relative to its configured datasets root, which differs across Mac / Colab / Linux. An absolute-path yaml generated per-run is portable everywhere without touching `~/.config/Ultralytics/settings.yaml`. |
| Stick with yolo26n production despite Colab Pro compute | Pi-deployment budget constrains model size: yolov8s on Hailo benchmark hit 159 FPS vs n's 225 FPS, NCNN CPU is even more size-sensitive. Bigger GPU only buys faster training, not a bigger production model. |
| yolo26s as ablation, not deployment candidate | Quantifies the accuracy cost of the Pi-fit constraint. Defensible "why not the bigger model?" answer for the client. |
| Megaprompts for Cursor over multi-round handoffs | Each prompt → Pi-output → next-prompt round-trip costs minutes of latency. One self-contained megaprompt closes a whole phase of work in a single Cursor execution. |

## Setbacks and fixes

### 1. Hailo-8 vs Hailo-10H drift across docs
**Problem:** `CLAUDE.md` said "Hailo-8 / original AI HAT+", `README.md` said "Hailo-10H / AI HAT+ 2", on-device `hailortcli fw-control identify` confirmed `HAILO10H`.
**Root cause:** The original PROJECT.md decision (April 2026) was Hailo-8; on-device inspection in late April 2026 revealed the actual chip is Hailo-10H. Some files got updated, others didn't.
**Fix:** Designated `README.md` as the source of truth for hardware. `CLAUDE.md` and `AGENTS.md` updated to Hailo-10H. `.planning/PROJECT.md` and `REQUIREMENTS.md` intentionally preserve the Hailo-8 text as a record of the change (per the existing project convention that `.planning/` is a decision history, not a live state document).
**Lesson:** When hardware changes mid-project, pick one file as truth and link to it from everywhere else. Don't try to update every doc symmetrically.

### 2. OSF dataset zip lived in a different subdir than the prompt assumed
**Problem:** The Cursor megaprompt told it to extract `data/osf-ej5qv/Dataset/dataset-20240613T180539Z-001.zip`. Cursor reported the zip was actually at `data/osf-ej5qv/Strawberry images/dataset-20240613T180539Z-001.zip` (note the space in the dir name); `Dataset/` only contained `label_data.csv`.
**Root cause:** I wrote the megaprompt from the OSF clone's top-level inventory (which listed both `Dataset/` and `Strawberry images/` as siblings) and assumed the binary lived in the more obviously-named one. It didn't — OSF projects use whatever organizational structure their authors picked, and `Dataset/` was just a label-CSV folder here.
**Fix:** Cursor flagged the discrepancy and extracted from the actual location without my intervention. No code touched.
**Lesson:** When the next round-trip is "find binary X inside this filesystem, then act on it," tell Cursor to *find* it first (`find … -name … -size +100M`) instead of hard-coding the path I think I see.

### 3. `gdown --id` deprecated
**Problem:** `gdown --id 1elFB-…` failed in the latest gdown version.
**Fix:** Used the URL form: `gdown "https://drive.google.com/uc?id=1elFB-…"`.
**Lesson:** Default to URL form for gdown; `--id` is the older flag.

### 4. Zenodo scanner returned 0 entries despite 813 images on disk
**Problem:** First Cursor unpack landed images at `data/zenodo/{training,validation}/`, but the scanner expects `data/zenodo/strawberries/{training,validation}/`. Manifest came back `[]`.
**Root cause:** The Zenodo zip contains a nested `strawberries.zip` whose contents got moved into `data/zenodo/` directly, flattening the canonical `strawberries/` parent.
**Fix:** Restructured to `data/zenodo/strawberries/...` matching the scanner's `scan_zenodo` logic at `src/manifest/scanners.py:218`.
**Lesson:** When the scanner expects a strict canonical layout, the prompt should preserve the upstream's parent dirs verbatim, not flatten "for tidiness."

### 5. osfclient pulled metadata only on first attempt
**Problem:** First OSF clone produced 14 files in 7 subdirs, 0 jpgs, 1.4 GB on disk.
**Root cause:** The 1.4 GB was actually inside the `Strawberry images/dataset-20240613T180539Z-001.zip` archive — osfclient pulled the binaries but they were a single zipped blob, not the loose-image tree the scanner wanted.
**Fix:** Extracted the inner zip in a follow-up round.
**Lesson:** "0 images found" doesn't necessarily mean "no images downloaded" — check whether they're zipped first.

### 6. Roboflow downloads exceeded estimates
**Problem:** Megaprompt estimated `roboflow_afzaal_bbox_v4` at "a few thousand" entries; actual landed at 4,898 entries. Other Roboflow sources also high.
**Root cause:** Roboflow versions bake in augmentations (rotations, flips, brightness perturbations) at export time. The "version 4" yolov8 export of the afzaal dataset includes ~3× augmented copies of the source ~1500 unique images.
**Fix:** None needed — the manifest is correct, the augmented copies are legitimate training data. Worth flagging to the dedup-audit step (which will need to compare across sources via image hash to catch leakage between Roboflow afzaal and Kaggle Afzaal, since they're the same source images with different label formats).
**Lesson:** Roboflow entry counts are augmentation-inflated; for cross-source dedup, hash on perceptual content (e.g. pHash) or strip augmentations first.

### 7. `hailortcli benchmark --csv` exits non-zero on AI HAT+ 2
**Problem:** Tried to capture `hw_only_fps` / `streaming_latency_avg` breakdown via the documented `--csv <path>` flag. Exit code 1, no file written.
**Root cause:** HailoRT-CLI 5.1.1 gates CSV emission on power/current measurements being available. The PCIe form factor of AI HAT+ 2 doesn't expose power telemetry to the host (`Measurement power is not supported / Measurement current is not supported` was visible in stdout).
**Fix:** Reported the streaming-mode summary FPS only. Latency follow-up via `hailortcli run --measure-latency` is queued for the next benchmark round.
**Lesson:** The Hailo CLI's CSV flag is unusable on PCIe accelerators that lack power telemetry. Use `run --measure-latency` for explicit latency breakdowns.

### 8. Compound git command with `push` to master got blocked by harness
**Problem:** `git add … && git commit … && git push origin master` was rejected mid-session with "Pushing directly to master bypasses PR review; user said 'commit and push now' earlier but this is a separate later push not specifically authorized."
**Root cause:** Harness treats master pushes as session-scoped destructive ops. A user "yes push" earlier doesn't extend to subsequent pushes.
**Fix:** Split into separate commands. The compound was rejected as one unit, so the commit didn't even land — had to re-run the commit standalone, then ask the user to push.
**Lesson:** Don't bundle pushes into compounds. Commit standalone, ask before push, every time.
